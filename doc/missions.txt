Mission 1: Who Are You?
Background: what are we learning?
Linux does not simply trust the name shown in a terminal. Each user account has a numeric user ID (UID) and
group ID (GID). Processes also carry effective credentials (EUID/EGID) used by the kernel when checking
permissions. Authentication is proving identity; authorization is deciding which actions that identity may perform.
The CIA triad refers to confidentiality, integrity, and availability.
Your job / completion goal
Compare the account shown by shell tools with the numeric identity printed by a C program, and connect a
credential to a security decision.
What you need before starting
Ubuntu terminal, gcc; no sudo needed.
Do these steps in order
Step 1. Open a terminal, create your assigned source directory and identify your account.
 whoami
id
groups
mkdir -p ~/securelab/member1/src ~/securelab/member1/evidence
Step 2. Create the file ~/securelab/member1/src/identity.c with the complete program below. Use nano or another
text editor.
 #include <stdio.h>
#include <unistd.h>
int main(void) {
    printf("Real UID         : %d\n", (int)getuid());
    printf("Effective UID    : %d\n", (int)geteuid());
    printf("Real GID         : %d\n", (int)getgid());
    printf("Effective GID    : %d\n", (int)getegid());
    return 0;
}
Step 3. Compile, run, then record a screenshot showing both `id` and the program output.
 cd ~/securelab/member1/src
gcc -Wall -Wextra identity.c -o identity
id
./identity
Step 4. Choose and describe two realistic workstation attack surfaces, such as an exposed network service or a
browser extension with broad permissions. Do not test or attack the example surfaces.
What you should observe
The numeric UID/GID values in `id` should normally match the corresponding real/effective values in this ordinary
process. If elevated execution changes effective credentials, record that difference rather than guessing.
What your explanation must establish
Explain: the UID identifies the owner; the effective UID is the identity consulted for many access checks. An
unauthorized read of a private file violates confidentiality. Include one example separating logging in from getting
permission to read a particular file.

Mission 2: Meet the Kernel
Background: what are we learning?
Normal programs run in user space and cannot arbitrarily modify protected kernel data or hardware. To request
controlled services, such as opening a file, a program enters the kernel through a system call. The kernel checks
relevant rules, carries out the operation, and returns a result. The trusted computing base (TCB) includes
components whose correctness matters to security.
Your job / completion goal
Create a file through C system calls, trace the program, and label the user-space/kernel boundary.
What you need before starting
Complete Mission 1; gcc and strace installed (`strace --version`).
Do these steps in order
Step 1. Create syscall_demo.c in your member1/src directory. The program uses open, write, and close explicitly.
 #include <fcntl.h>
#include <stdio.h>
#include <unistd.h>
int main(void) {
    int fd = open("hello.txt", O_CREAT | O_WRONLY | O_TRUNC, 0644);
    if (fd == -1) { perror("open"); return 1; }
    const char msg[] = "Hello from user space!\n";
    ssize_t n = write(fd, msg, sizeof(msg)-1);
    if (n < 0) { perror("write"); close(fd); return 1; }
    close(fd);
    return 0;
}
Step 2. Compile and run from a directory you own. Confirm that it created the output file.
 cd ~/securelab/member1/src
gcc -Wall -Wextra syscall_demo.c -o syscall_demo
./syscall_demo
cat hello.txt
Step 3. Run the same program under the system-call tracer; save the complete trace, then select relevant lines.
 strace -o ../evidence/m02_trace.txt ./syscall_demo
grep -E 'openat|write\(|close\(' ../evidence/m02_trace.txt | tail -20
Step 4. Make a four-box diagram on paper or in the final report: Application -> system call -> Linux kernel -> file
resource. Mark that the kernel mediates access.
What you should observe
`hello.txt` contains the written message. `strace` usually displays `openat`, `write`, and `close`; modern libc may
implement `open()` via `openat()`. The trace includes unrelated library-loading calls, so identify only the relevant
ones.
What your explanation must establish
Show the file descriptor returned on opening and used by write/close. Explain why the application relies on a
trusted kernel rather than directly accessing disk hardware.

Mission 3: Process Detective
Background: what are we learning?
Every process has a PID, parent PID (PPID), credentials, thread count, and resource usage. Linux exposes many
of these through the pseudo-filesystem `/proc`; the files reflect kernel process data rather than ordinary
documents saved on disk. An investigator can use these fields to find unexpectedly privileged or resource-hungry
processes.
Your job / completion goal
Build a process inspector that prints useful `/proc` fields, then add one extra piece of information as requested by
the handout.
What you need before starting
Ubuntu terminal; read access to one of your own processes. No sudo needed.
Do these steps in order
Step 1. Start a harmless sleep process in the background and save its PID. Do not pick an unrelated system
process.
 sleep 120 &
PID=$!
echo "My test PID is $PID"
ps -p "$PID" -o pid,ppid,uid,cmd
Step 2. Save the starter inspector as proc_inspector.sh. This includes the handout TODO completed with a
security-related field: effective capabilities (CapEff).
 #!/usr/bin/env bash
PID="$1"
if [ -z "$PID" ]; then echo "Usage: $0 <PID>"; exit 1; fi
if [ ! -d "/proc/$PID" ]; then echo "No such process"; exit 1; fi
echo "PID: $PID"
echo "Command: $(tr '\0' ' ' < "/proc/$PID/cmdline")"
grep -E '^(Name|State|PPid|Uid|Gid|Threads|VmSize|VmRSS):' \
    "/proc/$PID/status"
echo "FD count: $(ls "/proc/$PID/fd" 2>/dev/null | wc -l)"
grep '^CapEff:' "/proc/$PID/status"
Step 3. Run the inspector against your saved PID, then inspect the same fields directly in `/proc`.
 chmod +x proc_inspector.sh
./proc_inspector.sh "$PID"
cat "/proc/$PID/status" | head -25
ls -l "/proc/$PID/fd"
Step 4. Capture the output and stop the test process afterward. If using a new terminal, re-enter the recorded PID.
 kill "$PID"
What you should observe
The inspector should show a process name, parent PID, UID/GID, thread count, memory values (possibly
zero/omitted), descriptor count, and CapEff. PIDs disappear when the process exits. `fd` listing may be restricted
for processes owned by others.

Mission 4: Can One Process Read Another?
Background: what are we learning?
Each process sees a virtual address space containing code, data, stack, heap, and mapped libraries. A pointer
such as `0x...` is meaningful only within that process address space; it is not an unrestricted reference to all
physical memory. The memory-management unit (MMU), page tables, and kernel rules help enforce process
isolation.
Your job / completion goal
Observe a program address and its `/proc/PID/maps`, then explain why other normal processes cannot simply
use that pointer.
What you need before starting
Ubuntu terminal with two terminal windows; gcc; no root privileges required.
Do these steps in order
Step 1. Save address_space.c exactly as shown, in member1/src.
 #include <stdio.h>
#include <unistd.h>
int main(void) {
    int secret = 12345;
    printf("PID = %d\n", (int)getpid());
    printf("&secret = %p\n", (void *)&secret);
    printf("secret = %d\n", secret);
    printf("Inspect /proc/%d/maps for 30 seconds.\n",(int)getpid());
    fflush(stdout);
    sleep(30);
    return 0;
}
Step 2. Compile and run; note the PID while the program sleeps.
 gcc -Wall -Wextra address_space.c -o address_space
./address_space
Step 3. In a second terminal, replace 12345 with the *actual printed PID*. Save the memory map before 30
seconds elapse.
 cat /proc/12345/maps | head -35
cp /proc/12345/maps ~/securelab/member1/evidence/m04_maps.txt
Step 4. Make a labelled memory layout: program text; read-only/initialized data; heap; shared libraries; stack.
Locate `[stack]` in your own mapping if it is shown.
What you should observe
The map contains address ranges, permission letters such as `r-xp` and `rw-p`, offsets, and sometimes file
names or `[stack]`. Your pointer is typically inside a writable stack region. Addresses can differ between runs due
to ASLR.
What your explanation must establish
Explain the distinction between a virtual address and physical memory; a different process has different
mappings, and normal process isolation prevents direct dereferencing of its private memory.

Mission 5: The Race
Background: what are we learning?
When two threads increment the same ordinary variable without synchronization, both can read an old value and
overwrite each other's updates. This is a data race and is undefined behavior in C, so the observed count is not
guaranteed. A mutex creates a critical section in which only one thread at a time changes the shared counter.
Your job / completion goal
Run the counter without a mutex several times, then run a mutex-protected version and compare the result.
What you need before starting
gcc with pthreads; no sudo. Keep both versions or a clearly marked option.
Do these steps in order
Step 1. Create the unsafe demonstration race_demo.c and run it repeatedly. This version intentionally has a data
race for the lab.
 #include <pthread.h>
#include <stdio.h>
long counter = 0;
void *worker(void *arg) {
    (void)arg;
    for (long i=0; i<1000000; i++) counter++;
    return NULL;
}
int main(void) {
    pthread_t t1,t2;
    pthread_create(&t1,NULL,worker,NULL);
    pthread_create(&t2,NULL,worker,NULL);
    pthread_join(t1,NULL); pthread_join(t2,NULL);
    printf("Expected: 2000000\nActual: %ld\n",counter);
    return 0;
}
Step 2. Compile with optimization disabled. Record at least three actual outputs.
 gcc -Wall -Wextra -O0 -pthread race_demo.c -o race_demo
./race_demo
./race_demo
./race_demo
Step 3. Create a FULL second file named race_fixed.c (paste this entire version). Unlike the first run, every
increment occurs while the same mutex is held.
 #include <pthread.h>
#include <stdio.h>
long counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
void *worker(void *arg) {
    (void)arg;
    for (long i=0; i<1000000; i++) {
        pthread_mutex_lock(&lock);
        counter++;
        pthread_mutex_unlock(&lock);
    }

Mission 6: Two Processes Need to Talk
Background: what are we learning?
Inter-process communication (IPC) lets separate processes exchange data. A pipe carries a sequence of bytes
through kernel-managed endpoints; each side owns file descriptors. Shared memory exposes a common mapped
region to multiple processes, which avoids copying but usually requires explicit coordination. An IPC trust
boundary includes both its endpoints and the message contents.
Your job / completion goal
Run the supplied parent-to-child pipe example and compare its properties with shared memory conceptually, or
using an instructor-supplied example.
What you need before starting
Complete basic C compiling; no sudo. The handout says the shared-memory design will be supplied by the
instructor.
Do these steps in order
Step 1. Save the handout-style pipe program as pipe_ipc.c.
 #include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>
int main(void) {
    int fd[2];
    if (pipe(fd)==-1) { perror("pipe"); return 1; }
    pid_t pid=fork();
    if (pid==-1) { perror("fork"); return 1; }
    if (pid==0) {
        close(fd[1]);
        char buffer[128]={0};
        ssize_t n=read(fd[0],buffer,sizeof(buffer)-1);
        if (n>=0) printf("Child received: %s\n",buffer);
        close(fd[0]);
        return 0;
    }
    close(fd[0]);
    const char msg[]="Hello from the parent";
    if (write(fd[1],msg,strlen(msg)+1)==-1) perror("write");
    close(fd[1]);
    waitpid(pid,NULL,0);
    return 0;
}
Step 2. Compile, run, and capture what the child prints.
 gcc -Wall -Wextra pipe_ipc.c -o pipe_ipc
./pipe_ipc
Step 3. Annotate on the source: `pipe()` creates two descriptors; `fork()` starts a child; child closes write end and
reads; parent closes read end and writes. `waitpid()` waits for the child.
Step 4. Complete the comparison table in your report. If the instructor provides a shared-memory program, run it
and add its output; otherwise explicitly state it was not provided.

Mission 7: Alice vs Bob
Background: what are we learning?
Discretionary access control (DAC) is a model in which file owners can set permissions, within system policy.
Traditional Unix modes distinguish owner, group, and others; `r` allows reading, `w` modification, and `x`
execution (or directory traversal). Changing mode to 600 gives only the file owner read/write access.
Your job / completion goal
Create a test file with one account, check another account's read access before and after permission changes.
What you need before starting
ADMIN APPROVAL REQUIRED. Creating accounts on a shared campus PC is a system modification. Run only
on a designated lab machine with permitted sudo; otherwise obtain an instructor-approved substitute
environment.
Do these steps in order
Step 1. First check whether the names are already used. If either account exists and is not an
instructor-designated test account, STOP. With written permission only, create new test accounts.
 getent passwd alice || true
getent passwd bob || true
sudo adduser alice
sudo adduser bob
id alice
id bob
Step 2. Create Alice's file in /tmp with deliberately permissive access for the first observation. `chmod 644` makes
Bob's first read result unambiguous.
 sudo -u alice bash -c 'echo "Alice secret" > /tmp/alice_secret.txt'
sudo chown alice:alice /tmp/alice_secret.txt
sudo chmod 644 /tmp/alice_secret.txt
ls -l /tmp/alice_secret.txt
sudo -u bob cat /tmp/alice_secret.txt
Step 3. Restrict access and run the exact same test again.

#include <string.h>

    char buffer[16];
    const char input[] = "THIS_INPUT_IS_LONGER_THAN_SIXTEEN";

           strlen(input) + 1);

Your job / completion goal

cat config.sha256
sha256sum -c config.sha256

Mission 19: Harden the Machine
Background: what are we learning?
Hardening reduces unnecessary functionality and risk. Typical controls include patching software, disabling
unused services, restricting listening ports, and setting firewall rules. Good engineering records the baseline first,
changes only what is justified, and verifies the result afterward. On a shared campus computer, changing
system-wide settings can affect everyone.
Your job / completion goal
Perform a read-only baseline audit, plan at least three specific hardening changes, and apply only changes
explicitly approved for a dedicated test machine.
What you need before starting
ADMIN APPROVAL REQUIRED for actual changes. Do not disable network/SSH, install upgrades, or change
firewall rules on a shared lab PC without signed/clear instructor permission.
Do these steps in order
Step 1. Record the operating system, kernel, update availability, running services, open ports, and firewall status
BEFORE making any changes.
 date -Is
cat /etc/os-release
uname -r
sudo apt update
apt list --upgradable 2>/dev/null | head -30
systemctl --type=service --state=running --no-pager
ss -lntup
sudo ufw status verbose 2>/dev/null || true
Step 2. For each proposed change, note risk, why it is necessary, exact command/setting, how to undo it, and
how you would verify it. Example ideas: remove an unused test service, restrict a nonessential listening port, or
apply approved updates.
Step 3. On a DEDICATED approved system only, implement at least three justified changes and collect
before/after commands. On a shared PC, submit the documented hardening plan and explicitly state that no
disruptive change was permitted.
Step 4. Recheck the same baseline commands and compare exact services/ports/settings. Do not write “secured”
unless the intended condition was truly verified.
What you should observe
Baseline results depend on the machine. `apt update` refreshes package metadata and itself changes system
package-list state; if even this is not approved, use existing `apt list --upgradable` only and label the limitation.
What your explanation must establish
Patches close known weaknesses; fewer unnecessary services reduce attack surface; documented reversibility
protects availability. A denied administrative change must be reported as blocked, not recorded as done.

Mission 20: Secure Remote Access
Background: what are we learning?
SSH lets a user establish an encrypted remote login session. The server authenticates the connecting user and
the client normally verifies the server host key; afterward Unix permissions and other policies determine what that
user may do. Login events may appear in system logs.
Your job / completion goal
Test SSH against localhost on an approved machine without opening it to the internet.
What you need before starting
ADMIN APPROVAL REQUIRED if the SSH server must be installed or enabled; existing localhost SSH is safest.
Avoid external network exposure.
Do these steps in order
Step 1. Inspect whether sshd is available and listening on port 22, without changing configuration.
 command -v sshd || true
sudo systemctl status ssh --no-pager
ss -lnt | grep ':22' || true
Step 2. If the server is installed and staff permits local login, connect to localhost with your own lab account. Verify
the host fingerprint through your administrator before accepting an unexpected new key.
 ssh localhost
Step 3. Inside that SSH session, show the username and hostname; exit. Then inspect accessible logs for the
authentication event.
 whoami
hostname
exit
journalctl -u ssh --since "15 minutes ago" --no-pager | tail -30
Step 4. Explain the difference between successfully proving identity and subsequently being allowed to edit
particular files.
What you should observe
Successful SSH should open a local shell after valid authentication; failures can reflect server not running,
key/password policy, or missing privileges. Do not lower authentication requirements just to force the demo.
What your explanation must establish
SSH provides encrypted access and identity checks, while authorization is still enforced by the guest Linux
permissions, ACLs and system policy.

Mission 21: Who Protects the VM?
Background: what are we learning?
Virtualization adds a boundary between a guest operating system and the physical machine. A hypervisor
provides virtual CPUs, memory, storage and devices; a guest kernel relies on that virtual hardware. The security
chain extends through guest software to the hypervisor and host. Native Ubuntu on a lab workstation has a
different architecture: no guest VM/hypervisor layer is necessarily present.
Your job / completion goal
Draw the virtualization trust stack requested by the handout and distinguish it from the native Ubuntu lab
environment actually used by your team.
What you need before starting
Conceptual exercise. To observe an actual guest/hypervisor relationship, the instructor must provide an
authorized VM or approve a demonstration environment.
Do these steps in order
Step 1. Record whether you are on native Ubuntu or a virtual guest, based on the lab setup rather than
assumptions.
 cat /etc/os-release
systemd-detect-virt || true
uname -a
Step 2. Draw the handout-required stack with arrows and labels: Application -> guest kernel -> virtual hardware ->
hypervisor -> host/physical hardware. Identify the trust boundaries.
Step 3. Next to it, draw the actual lab stack: Application -> native Ubuntu kernel -> physical hardware. If Ubuntu is
already virtualized, label the actual layers correctly.
Step 4. Write a paragraph on the additional VM attack surface: hypervisor bugs, virtual devices, management
controls, host patching, guest-to-host boundaries.
What you should observe
`systemd-detect-virt` may print a virtualization type, `none`, or return a nonzero code. On a native workstation you
cannot collect a genuine guest hypervisor trace; a well-labelled conceptual diagram is honest but may need
instructor approval as a substitute.
What your explanation must establish
Guest kernel and privileged guest services are inside a guest trust boundary; the hypervisor mediates virtual
hardware. Virtualization is helpful isolation but adds components that must also be secured.
Two trust stacks
 Required VM model: app -> guest kernel -> virtual hardware -> hypervisor -> host/hardware
Actual native lab model: app -> Ubuntu kernel -> physical hardware
Label first as CONCEPTUAL if no guest VM was provided.
