Welcome to SECURELAB 
Traditional security courses often begin with definitions: authentication, authorization, DAC, MAC, ASLR, 
sandboxing, and so on. SECURELAB reverses the order. You will first encounter a security problem, experiment 
with a real Linux system, observe what happens, and then connect the observation to the operating-system 
concept. 
The SECURELAB learning loop 
QUESTION → OBSERVE → EXPERIMENT → CONNECT → SECURE → VERIFY 
 
What you will build 
 A Linux virtual machine that acts as your security laboratory. 
 Small C and Bash programs that expose operating-system mechanisms. 
 A collection of evidence showing what you observed and why it happened. 
 A progressively hardened Linux environment. 
 A final security assessment in which you must investigate and fix problems with less scaffolding. 
What you are NOT expected to do 
 You do not need to become a professional security tester (unless you want to) 
 You do not need to write malware (GOD is watching you, shame on you!) 
 You do not need to exploit public systems (Tch tch tch! Don’t even think about it) 
 You do not need to memorize every Linux command. 
 
What you are expected to do 
Code (a bit), understand and explain what the operating system is doing and provide evidence for your 
conclusions. 
Golden rule 
Experiment only inside your own VM, your Linux machine or an environment explicitly authorized by your 
instructor. Never scan, attack, exploit, or deliberately disrupt systems you do not own or have permission 
to test.

Mission 6: Two Processes Need to Talk 
Syllabus connection: secure IPC, message passing, shared memory, synchronization 
Mission objective: Compare IPC mechanisms and identify the security properties of the communication 
endpoint. 
Concepts: IPC, pipe/message passing, shared memory, permissions, trust boundary 
Experiment 
Use a simple pipe-based IPC first; then compare it with the shared-memory design supplied by your instructor. 
Starter code 
# pipe_ipc.c 
#include <stdio.h> 
#include <string.h> 
#include <unistd.h> 
#include <sys/wait.h> 
 
int main(void) { 
    int fd[2]; 
    if (pipe(fd) == -1) { 
        perror("pipe"); 
        return 1; 
    } 
 
    pid_t pid = fork(); 
    if (pid == -1) { 
        perror("fork"); 
        return 1; 
    } 
 
    if (pid == 0) { 
        close(fd[1]); 
 
        char buffer[128] = {0}; 
        ssize_t n = read(fd[0], buffer, sizeof(buffer) - 1); 
        if (n >= 0) 
            printf("Child received: %s\n", buffer); 
 
        close(fd[0]); 
        return 0; 
    } 
 
    close(fd[0]); 
 
    const char msg[] = "Hello from the parent";  
    if (write(fd[1], msg, strlen(msg) + 1) == -1) 
        perror("write"); 
 
    close(fd[1]); 
    waitpid(pid, NULL, 0); 
    return 0; 
}

Mission 22 — FINAL CHALLENGE: Secure the Machine 
The scaffolding ends here. Your team receives a Linux VM or instructor-prepared snapshot containing several 
weaknesses. Your task is to investigate, explain, fix, and verify. 
The challenge 
Do not begin by changing everything. First establish a baseline. A security engineer needs evidence 
before remediation. YOU WILL BE GIVEN A SEPARATE DOCUMENT WITH ALL THE RULES AND

Your workflow 
68. Establish a baseline: users, processes, services, listening ports, important files, and security status. 
69. Identify at least five security observations. 
70. Classify each observation: confidentiality, integrity, availability, authentication, authorization, isolation, or 
attack surface. 
71. Choose an appropriate OS-level control. 
72. Apply the control. 
73. Re-test the original condition. 
74. Capture evidence. 
75. Write a short security report. 
Possible findings

 A file can be modified without adequate detection. 
 An unnecessary network service is listening. 
 An application is insufficiently confined. 
 Logs are insufficient to reconstruct an event. 
 Security updates are missing.

Part V — Troubleshooting 
Problem First response 
VM is slow Close host applications; check VM RAM/CPU 
allocation; avoid running several heavy tools at 
once. 
No network Check VM network mode; run `ip a`, `ip route`, then 
`ping -c 3 ubuntu.com`. 
Permission denied Run `id`; inspect `ls -l`, directory permissions, 
ownership and ACLs. 
Command not found Check the mission's package installation step; use 
`apt search <term>`. 
Service will not start Use `systemctl status <service>` and `journalctl -u 
<service>`. 
C program differs from a friend's Record compiler version and flags. Repeat the 
experiment. Do not assume one run is universal. 
I broke the VM Stop changing things. Revert to your latest known-
good snapshot. 
Docker behaves unexpectedly Check the Docker installation path and whether the 
daemon is running. Use the official Docker 
documentation. 
Good evidence habits 
 Capture the command and the output together. 
 Record both insecure and secured states. 
 Write your prediction before running an experiment. 
 If the result varies, repeat it and explain why. 
 A screenshot without an explanation is not sufficient evidence.

 Use `-g` when debugging with GDB. 
 Use `-pthread` for POSIX thread programs. 
 Record important compiler flags when comparing security protections. 
 Do not copy exploit payloads from the internet into lab programs. 
 Keep intentionally unsafe programs inside the VM.
